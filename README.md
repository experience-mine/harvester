# project-snapshot

Агент снимает состояние программного проекта: обходит рабочую копию, собирает факты об истории,
файлах, зависимостях и документах, подтверждает каждый факт источником и выгружает один
машиночитаемый документ — слепок проекта.

## Быстрый старт

Ничего ставить не нужно: агент, `git` и утилита анализа кода `tldr` уже внутри образа.

```bash
docker pull ghcr.io/united-software-platform/project-snapshot:latest

docker run --rm \
  -u "$(id -u):$(id -g)" \
  -v /путь/к/проекту:/project:ro \
  -v "$PWD/out:/out" \
  ghcr.io/united-software-platform/project-snapshot:latest
```

Слепок появится в `./out` каталогом прогона вида `backend/20260825120000-b2564d07/`; полный путь
печатается последней строкой прогона. Что лежит внутри — см. [состав каталога результатов](#что-попадает-в-каталог-результатов).

Три вещи в этой команде важны:

- `-v …:/project:ro` — проект монтируется **только на чтение**, агент в нём ничего не меняет;
- `-v "$PWD/out:/out"` — каталог результатов, единственное место записи;
- `-u "$(id -u):$(id -g)"` — файлы результата принадлежат вам, а не пользователю root внутри контейнера.

## Что делает

Слепок проекта — зафиксированное на момент прогона состояние проекта. После создания он неизменяем:
новое состояние даёт новый слепок, частичное обновление не поддерживается.

В слепок входят репозиторий и его история, участники, каталоги и файлы с ролями и хэшами, связи
между ними и подтверждения источников. Зависимости, технологии, миграции, документы и требования
предусмотрены форматом и наполняются по мере подключения анализаторов.

> **Важно:** источник истины — рабочая копия проекта. Слепок целиком пересобирается при каждом
> прогоне; агент никогда не читает собственную выгрузку обратно.

## Образ и его теги

```text
ghcr.io/united-software-platform/project-snapshot:latest    последняя сборка ветки по умолчанию
ghcr.io/united-software-platform/project-snapshot:v1.0.3    конкретный выпуск
ghcr.io/united-software-platform/project-snapshot:1.0       последний выпуск серии
ghcr.io/united-software-platform/project-snapshot:sha-85d6f30   точное соответствие коммиту
```

Для повторяемых прогонов берите `vX.Y.Z` или `sha-…`: `latest` меняется с каждой сборкой, и слепки,
снятые разными версиями агента, могут отличаться составом фактов.

Патч наращивается автоматически при каждой сборке ветки по умолчанию, мажор и минор задаются полем
`version` в `pyproject.toml`.

## Сценарии запуска

Во всех примерах `/путь/к/проекту` — анализируемая рабочая копия, `./out` — каталог результатов.
Создайте `./out` заранее: docker создаёт недостающий каталог монтирования от имени root, и запуск
под своим идентификатором пользователя записать в него не сможет.

**Слепок и анализ кода вместе.** Флаг `--code` добавляет разбор кода утилитой `tldr`:

```bash
mkdir -p out
docker run --rm \
  -u "$(id -u):$(id -g)" \
  -v /путь/к/проекту:/project:ro \
  -v "$PWD/out:/out" \
  ghcr.io/united-software-platform/project-snapshot:latest --code
```

**Исключить чужой код.** Всё после `--` уходит команде `snapshot export` без изменений:

```bash
docker run --rm \
  -u "$(id -u):$(id -g)" \
  -v /путь/к/проекту:/project:ro \
  -v "$PWD/out:/out" \
  ghcr.io/united-software-platform/project-snapshot:latest -- \
    --exclude 'vendor/' --exclude 'node_modules/'
```

**Кто есть в истории.** Перечень участников до сборки слепка; каталог результатов не нужен — команда ничего не пишет:

```bash
docker run --rm \
  -v /путь/к/проекту:/project:ro \
  --entrypoint snapshot ghcr.io/united-software-platform/project-snapshot:latest \
  authors /project
```

Вывод — строка на человека: число коммитов, имя и адрес, в порядке убывания числа коммитов.
Полученные значения подставляются в `--author` при сборке слепка.

**История одного человека.** Карта тождества сводит его учётные записи, отбор берёт их все:

```bash
docker run --rm \
  -u "$(id -u):$(id -g)" \
  -v /путь/к/проекту:/project:ro \
  -v "$PWD/out:/out" \
  ghcr.io/united-software-platform/project-snapshot:latest -- \
    --identity 'Иванов Иван=i.ivanov@example.com,ivanov@personal.example' \
    --author 'Иванов Иван'
```

В `--author` указывается имя личности из `--identity`: отбор раскрывается по карте тождества
и берёт все её адреса и написания имени. Любой из адресов человека даёт тот же результат, но имя
личности прямо связывает отбор с картой и не выглядит выбором одного адреса из двух.

**Проверить готовый слепок.** Команда агента вызывается напрямую, проект монтировать не нужно:

```bash
docker run --rm -v "$PWD/out:/out" \
  --entrypoint snapshot ghcr.io/united-software-platform/project-snapshot:latest \
  validate /out/backend/20260825120000-b2564d07
```

**Заглянуть внутрь образа:**

```bash
docker run --rm -it --entrypoint bash ghcr.io/united-software-platform/project-snapshot:latest
```

## Опции

Опции обвязки — управляют прогоном целиком:

| Опция | Назначение |
|-------|------------|
| `--code` | выполнить анализ кода утилитой `tldr` |
| `--code-path ПУТЬ` | что анализировать `tldr`, относительно проекта (по умолчанию `src`, иначе корень) |
| `--no-export` | пропустить слепок, оставить только анализ кода |
| `SCAN_MAX_ITEMS` | переменная окружения: предел рёбер графа вызовов, по умолчанию 100000 |
| `--out ПУТЬ` | каталог результатов внутри контейнера (по умолчанию `/out`) |
| `--project ПУТЬ` | анализируемый проект внутри контейнера (по умолчанию `/project`) |
| `-- …` | всё после двойного дефиса передаётся команде `snapshot export` |

Опции агента — управляют составом слепка, указываются после `--`:

| Флаг | Назначение |
|------|------------|
| `--exclude ШАБЛОН` | исключить пути из обхода; флаг повторяется |
| `--author ИМЯ_ИЛИ_ПОЧТА` | оставить в истории коммиты названных авторов; значение раскрывается по карте тождества до всех учётных записей личности; флаг повторяется |
| `--identity 'Имя=почта,почта'` | свести учётные записи одного человека; флаг повторяется |
| `--no-requirements` | не обращаться к модели за требованиями |
| `--quiet` | не выводить прогресс |
| `--versioned` | писать результат каталогом прогона `{slug}/{метка времени}-{отпечаток}` (обвязка включает его сама) |

Опции команды `authors` — перечень участников истории, выгрузка не собирается:

| Флаг | Назначение |
|------|------------|
| `--identity 'Имя=почта,почта'` | свести учётные записи одного человека; флаг повторяется |
| `--config ФАЙЛ` | конфигурация вместо `agent.yml` в корне проекта |
| `--format text|json` | вид перечня: строки либо JSON с полным перечнем написаний имени и адреса |

Коды возврата прогона со слепком: `0` — готово, `1` — ошибка запуска, `2` — валидация не пройдена,
`3` — модель недоступна, а обращение к ней требовалось.

Коды возврата команды `authors`:

| Код | Когда возвращается |
|-----|--------------------|
| `0` | перечень выведен; сюда же относится репозиторий без коммитов — в поток ошибок печатается «история пуста: авторы не найдены» |
| `1` | каталог недоступен, не является рабочей копией git (нет `.git`), не найден исполняемый файл `git`, неверна конфигурация или неверен формат `--identity`; сюда же — отказ git при чтении истории, его текст печатается после «история не прочитана» |

Коды `2` и `3` команда не использует: выгрузка не собирается и к модели она не обращается.

## Что попадает в каталог результатов

Каждый прогон получает собственный каталог `{slug проекта}/{метка времени}-{отпечаток фильтров}/`.
Прогоны не смешиваются и не перезаписывают друг друга, а каталог переносится в объектное
хранилище копированием «как есть»: путь становится ключом объекта.

Отпечаток берётся от применённых фильтров, поэтому два прогона одного проекта, различающиеся
только отбором по автору, различимы по имени каталога, без чтения содержимого файлов.

```text
snapshot/backend/20260830222458-b2564d07/
├── manifest.json               перечень объектов, провенанс и охват прогона
├── core.json.gz                скалярная часть: проект, репозитории, ветки, теги, участники
├── commits.jsonl.gz            секции выгрузки: одна запись — одна строка
├── directories.jsonl.gz
├── files.jsonl.gz
├── relationships.jsonl.gz
├── evidence.jsonl.gz
├── code_units.jsonl.gz
├── findings.jsonl.gz
├── … (technologies, dependencies, migrations, database_objects, documents, requirements)
└── code-analysis/              исходные документы анализа кода
    ├── tldr-structure.json.gz
    ├── tldr-calls.json.gz
    └── tldr-health.json.gz
```

### Объекты прогона

| Объект | Содержание |
|--------|------------|
| `manifest.json` | перечень объектов прогона, провенанс и охват анализа; единственный несжатый объект |
| `core.json.gz` | скалярная часть документа и малые секции: версия схемы, время выгрузки, фильтры, проект, репозитории, ветки, теги, участники, охват анализа |
| `{секция}.jsonl.gz` | массивная секция выгрузки построчным JSON: одна запись — одна строка, без форматирующих отступов, порядок задан идентификатором записи |
| `code-analysis/tldr-structure.json.gz` | классы, методы с сигнатурами и импорты |
| `code-analysis/tldr-calls.json.gz` | граф вызовов: узлы и рёбра с типом вызова |
| `code-analysis/tldr-health.json.gz` | метрики кода: сложность, связность, мёртвый код, дублирование |
| `code-analysis/tldr-{команда}.err.gz` | диагностика команды анализа, завершившейся с ошибкой |

Секция без записей не пропадает, а записывается объектом с нулём строк: отсутствие объекта нельзя
отличить от несобранной секции. Сжатие пообъектное, общего архива нет — иначе выборочное чтение,
ради которого сделано разбиение, стало бы невозможным.

Основные факты анализа кода нормализованы в секции `code_units`, `findings` и `relationships`
выгрузки. Исходные документы `tldr` сохраняются рядом потому, что нормализация переносит не всё:
разбивка связности по компонентам и поимённые списки вызовов в парах в модель не ложатся, а слепок
неизменяем и пересоздаётся только полным прогоном по рабочей копии.

### Назначение манифеста

Манифест делает каталог прогона самодостаточным: состав результатов, их происхождение и охват
анализа определяются по нему, без чтения секций.

| Раздел | Содержание |
|--------|------------|
| `objects` | имя, размер, `sha256` и тип содержимого каждого объекта, а для секций — число записей. Перечень формирует записывающая сторона, поэтому посторонние файлы каталога в него не попадают, а загрузчик проверяет целостность переноса, не разбирая формат выгрузки |
| `provenance` | время начала и завершения, версии агента, `tldr` и `git`, координата образа, его тег, ревизия сборки и `digest`, полный состав фильтров и параметры запуска. Версия агента задана константой в коде и две сборки не различает — это делают ревизия и `digest` |
| `analysis_scope` | чем и какая часть проекта проанализирована, какой язык покрыт, какие разделы выполнены, усечён ли граф вызовов и сколько фактов отброшено из-за ссылок на файлы вне выгрузки |
| `sections` | число записей в каждой секции: объём секции узнаётся без её загрузки |

Охват анализа существен потому, что `tldr` разбирает один подкаталог и один язык, тогда как агент
обходит весь репозиторий. Без него счётчики анализа читались бы как характеристика всего проекта,
а файл вне области анализа не отличался бы от файла без определений. Охват записывается и тогда,
когда все команды анализа завершились с ошибкой: отсутствие архитектурной части определяется
по манифесту, а не по отсутствию файлов в каталоге.

> **Примечание:** если каталог результатов находится внутри анализируемого проекта, обвязка сама
> исключает его из обхода — иначе файлы предыдущего прогона попали бы в следующий слепок.

## Запуск через docker compose

Способ для регулярных прогонов: пути задаются один раз в `.env`.

```bash
cp .env.example .env      # укажите PROJECT_DIR — путь к анализируемому проекту
docker compose pull
docker compose run --rm scanner --code -- --exclude 'vendor/'
```

Те же действия через `make`:

```bash
make pull                                             # получить образ из реестра
make scan                                             # только слепок
make scan-code SCAN_ARGS="-- --exclude 'vendor/'"     # слепок и анализ кода
make shell                                            # оболочка внутри образа
```

## Разработка

Локальная сборка образа вместо готового:

```bash
docker compose build     # или: docker build -t project-snapshot .
```

Запуск агента без контейнера — нужен Python 3.12 и старше плюс установленный `git`:

```bash
pip install .
snapshot export /путь/к/проекту --versioned -o ./out
```

Приёмочные проверки создают временные репозитории, прогоняют агент и сверяют результат с самим `git`:

```bash
python tests/step1_acceptance.py
python tests/step2_acceptance.py
```
